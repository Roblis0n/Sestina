# Operating the G1–G3 foundation and continuing at G4

This is the opt-in development foundation on `codex/post-0.2-g1-g3`, starting
at G0 `a4889ee996064d95ee0a3fb470ee6ee12d3a91a3`. It does not switch the shipped
Research Room, migrate a user's project automatically, or publish a new release.
Use synthetic disposable projects for development. Completion evidence belongs
in [G1–G3 evidence](G1-G3-EVIDENCE.md) and [gate status](IMPLEMENTATION-STATUS.md).

## Reproducing the old release fixture

Create a detached source worktree at the exact release commit under this
checkout's ignored `.tmp/` area, and install the dependencies declared by that
old checkout. For example, use `git worktree add --detach
.tmp/g1-legacy-release-source caf893db7928bab91c4098eb04a7e4a8d4c62ffe`.
All Sestina dependency links must resolve inside that old worktree; the recipe
checks them before building. The recorded Node/esbuild/TypeScript versions and
the old dependency lock identify the reproduction environment.

Run `pnpm test:post-0.2:legacy-release .tmp/g1-legacy-release-source`. This runs
the old build script twice, verifies deterministic archives, and compares every
release file against `legacy-release-provenance.json`. Keep generated archives
and databases ignored. The public gate uses `--verify-inputs` to check the pinned
full source archive and complete recipe without requiring a second installed
checkout on every runner. `--freeze` was used only for the initial reviewed
declaration; it must not be used to conceal changed source or toolchain results.

The recorded fixture was rebuilt and reproduced on Windows x64. It represents
exact old code with synthetic/no project data. It is not a downloaded release,
and its hashes do not claim equivalence to the original GitHub Release assets.

## Migration and recovery entry points

The public `@sestina/core` package exports the following operations. No operation
contacts a Provider or retries a network request.

1. `previewKernelMigration(projectRoot)` inspects a copied snapshot, including
   committed WAL data. It reports project identity, source schema, source hashes,
   space estimate, and every old table's row count, exact-content fingerprint and
   preservation/history/derived disposition. It does not modify the original.
2. `migrateKernelProject({ projectRoot })` repeats preflight, obtains the existing
   maintenance boundary and a SQLite writer fence, verifies that the source has
   not changed, saves and verifies a pre-migration backup, and migrates a separate
   staging database through 021–025. Canonical/legacy mapping and full validation
   finish before the active pair can be replaced.
3. `openKernelProject(projectRoot, readOnly)` validates schema structure, journal,
   project binding, database integrity, references, canonical chain and Brief
   projection before returning a handle. Ordinary opens refuse incomplete work.
4. After an interruption, explicitly call `recoverKernelMigration(projectRoot)`.
   It returns `swapped` only for the verified complete target pair, or
   `rolled_back` for the intact/restored verified old pair. It does not continue
   SQL in a half-migrated database. Unknown databases, Brief files and unrecorded
   WAL data remain preserved and produce `recovery_required`.
5. `restoreKernelPreMigrationBackup(projectRoot)` explicitly restores the verified
   old backup. It does not run reverse migrations. A post-migration privacy
   redaction blocks this operation so that restoring an older Memory body cannot
   silently undo a user's Forget. Later copy cleanup belongs to G7.

The external `.kernel-migration.json` journal describes the intended operation,
durable stage and switch progress. The active SQLite/Brief pair, staging copy,
original pair and verified backup have separate locations under the recognized
project store. The journal and maintenance fence make the multi-file switch
atomic to supported readers/writers; this is not a claim that two filesystem
renames form one operating-system operation. Every partial rename has an
executable process-death/recovery test. Never edit the journal to force an open.

The supported compatibility corpus is schema 16–20 generated by the pinned
`v0.2.0` source. Unknown table/trigger structures, future or partial migration
journals, corrupt inputs and missing Brief binding are refused. Legacy accepted
and modified-accepted outcomes become explicitly lossy, historical disposed
Reviews, without manufacturing Decisions or Evidence. Migration creates exactly
one revision-1 baseline. Original legacy payloads and hashes remain readable.

| Reported result | Required handling |
| --- | --- |
| `maintenance_busy` / `source_changed` | Preserve the project; stop the competing writer and explicitly start a new preflight. |
| `too_new` / `partial_schema` / `invalid_project` | Do not rewrite or initialize the directory. Inspect a verified copy with a compatible runtime. |
| `migration_failed` | Preserve source, journal and backups; use explicit recovery. |
| `recovery_required` | Keep writes closed. Do not guess which database or WAL is authoritative. |

## Persistence and transaction use

Create the existing `ResearchUnitOfWork` from `@sestina/research-store` over an
opened target database. Its `kernel` member is present only on the opt-in target.
`kernel.workflow(...)` saves Reviews, Manifests, attempts and corrections without
advancing the research revision. It cannot acquire canonical write permission.
Legacy Room/Pilot/Appeal writers are refused at both repository and SQL boundaries.
The old records remain available through validated read-only compatibility views.

`kernel.commitCanonical(command, synchronousRepositoryWork)` is the G3 primitive
for one future Kernel command. The command binds the expected project revision,
Review version, confirmed object versions, effect identity and preview hash.
The Kernel's live local-session authorization callback defaults to deny; Memory,
privacy and Episode governance use a separate callback. These callbacks are not
public IPC or model capabilities and must never be supplied from untrusted input.

Repository object changes, Memory/Brief metadata, privacy records, the terminal
Review, revision event/head, Receipt, command identity and projection outbox share
one SQLite transaction. Failure rolls everything back. The event is the technical
Trace behind the Receipt; there is no second authoritative trace store. A Receipt
includes its exact Manifest identity and assessment attempt reference, but no
outbound body or hidden reasoning. Unknown assessment outcomes remain unavailable.

On `stale_revision` or `stale_object`, retain the draft and return the conflict to
the user for a new preview. Do not auto-rebase or auto-approve. On
`commit_uncertain`, call `kernel.lookupCommand(projectId, authorityCommandId)`;
the durable command identity and Receipt resolve whether that exact command
committed. Repeating a matching identity returns the first result without
executing repository work or advancing the revision again. Conflicting reuse fails.

`readKernelSnapshot` reads and validates one transaction snapshot.
`projectKernelContext` computes a deterministic, bounded policy-1 projection from
that snapshot. Explicit Issue/Evidence selection and Memory identity/version/hash
are durable Manifest inputs; a no-Provider Manifest retains them too. A projection
hash is an identity check, not semantic validation. G5 still owns preparing the
actual Provider request and comparing all four identity layers immediately before
any send. A saved confirmation never causes a send on startup.

`recoverKernelWorkflows` changes interrupted running attempts to uncertain once,
without research revision changes or network activity. Derived views carry their
source revision; failed or stale rebuilds are reported as rebuilding and cannot
change canonical state. A known older Brief file is likewise a derived cache;
unknown content fails validation. G6 owns publication of the rebuilt Brief file.

## Exact G4 continuation

Start from [effect contract 01](contracts/01-canonical-effects.json),
[revision contract 03](contracts/03-project-state-revision.json) and the G4 step
in plan 14. Implement the six typed effect handlers in the Kernel over the
existing domain constructors and `ResearchUnitOfWork.kernel.commitCanonical`.
Do not add another store, transaction owner, Receipt-only acceptance path, or
Provider prerequisite for a legitimate user choice.

Persist an explicit effect draft and object versions in the Review, produce a
user-inspectable preview from one snapshot, obtain live user authority, and commit
the exact approved result. Keep `record_only` distinct from object-creating
acceptance. Reuse the existing Brief aggregate and canonical `argument_evidence`
repository. Full semantic validation of each effect's business fields, application
service wiring and user-facing error projection are G4 work, not G3 completion.

Run `pnpm test:post-0.2:foundation` and `pnpm verify:public` as regression gates.
Use `pnpm test:post-0.2:downstream` and its discovery mapping to turn the G4 generic
acceptance/Provider-veto assertions GREEN as the real production entry adopts the
Kernel. Keep G5–G13 gaps explicit until their own implementations pass. In
particular, Provider orchestration, task-first UI, Electron and final production
cutover are not supplied by this foundation.
